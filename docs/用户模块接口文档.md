# 用户模块接口文档

## 一、通用约定

### 1.1 基础信息

| 项目 | 说明 |
|---|---|
| 基础路径 | http://localhost:8080 |
| 请求格式 | application/json |
| 响应格式 | application/json |
| 字符编码 | UTF-8 |

### 1.2 认证方式

登录成功后返回 token，需要登录的接口在请求头中携带：

| 请求头 | 值 |
|---|---|
| Authorization | Bearer {token} |

token 中携带当前登录用户的 id、用户名和角色，服务端据此确定「当前用户」，因此路径中不出现用户 id。这样设计可以从结构上避免越权修改他人数据。

token 由登录接口签发，采用 JWT（HS256 签名），有效期 120 分钟。

### 1.3 统一响应结构

所有接口返回同一结构：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": null
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| code | int | 业务状态码 |
| msg | string | 提示信息，失败时说明原因 |
| data | object / array / string / null | 业务数据，失败时为 null |

两条约定：

- HTTP 状态码统一返回 200，具体结果以响应体中的 code 为准。
- 前端判断成败应依据 code，msg 仅用于向用户展示。

### 1.4 业务状态码

| code | 含义 |
|---|---|
| 200 | 成功 |
| 400 | 请求参数不合法，或业务校验未通过（如密码错误） |
| 401 | 未登录或 token 无效 |
| 404 | 资源不存在（如用户名不存在） |
| 409 | 资源冲突（如用户名已存在） |
| 500 | 服务器内部错误 |

说明：401 在本项目中**专指「未登录或 token 无效」**，用于需要登录态的接口。登录接口本身不需要登录态，凭证错误属于业务校验失败，因此使用 400 和 404，不使用 401。

### 1.5 角色说明

| 数据库中的值 | 名称 | 说明 |
|---|---|---|
| READER | 借书者 | 默认角色，注册时由服务端写入，不接受前端传值 |
| ADMIN | 图书管理员 | 负责图书与借阅管理 |

说明：系统中不存在「系统管理员」角色。数据库中的 `ADMIN` 实际含义是图书管理员，字面上容易误读为系统管理员。

## 二、接口列表

| 序号 | 方法 | 路径 | 说明 | 需要登录 |
|---|---|---|---|---|
| 1 | POST | /users/login | 登录 | 否 |
| 2 | POST | /users | 注册用户 | 否 |
| 3 | GET | /users/me | 查询当前用户信息 | 是 |
| 4 | PATCH | /users/me/password | 修改当前用户密码 | 是 |
| 5 | PUT | /users/me/email | 修改当前用户邮箱 | 是 |

## 三、接口详情

### 1. 登录

**POST /users/login**

校验用户名与密码，通过后签发 token。

**请求头**

| 请求头 | 值 |
|---|---|
| Content-Type | application/json |

**请求体**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| name | string | 是 | 用户名 |
| password | string | 是 | 密码明文，服务端 MD5 后与库中哈希比对 |

**请求示例**

```json
{
  "name": "张三",
  "password": "abc123456"
}
```

**成功响应**

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": "eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxIn0..."
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| data | string | token 字符串，后续请求放在 Authorization 头中 |

data 直接就是 token，没有再包一层对象。

**失败情况**

| code | msg | 触发条件 |
|---|---|---|
| 400 | 用户名和密码不能为空 | name 或 password 为空 |
| 404 | 用户名不存在 | 用户名未注册 |
| 400 | 密码错误 | 用户名存在，但密码不匹配 |

**补充说明**

- 登录失败不使用 401，理由见 1.4。
- 服务端先判断用户名是否存在，再比对密码，两步分别返回 404 和 400，提示不同便于前端定位问题。代价是可以通过这两个码的差异探测某个用户名是否已注册。
- 密码比对方式：把前端传来的明文做 MD5，与库中存储的哈希值比较，不存储也不传输明文。

### 2. 注册用户

**POST /users**

借书者自助注册。服务端固定将 role 写为 READER，客户端无需也无法指定角色。

**请求头**

| 请求头 | 值 |
|---|---|
| Content-Type | application/json |

**请求体**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| name | string | 是 | 用户名，全局唯一，长度 1-50 |
| password | string | 是 | 密码明文，长度 6-20，服务端 MD5 后存储 |
| email | string | 是 | 邮箱，全局唯一，需符合邮箱格式，长度不超过 100 |

**请求示例**

```json
{
  "name": "张三",
  "password": "abc123456",
  "email": "zhangsan@example.com"
}
```

**成功响应**

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": null
}
```

**失败情况**

| code | msg | 触发条件 |
|---|---|---|
| 400 | 用户名不能为空 | name 缺失、为空或全为空格 |
| 400 | 用户名长度不能超过 50 | name 长度超过 50 |
| 400 | 密码不能为空 | password 缺失、为空或全为空格 |
| 400 | 密码长度需为 6-20 位 | password 长度不符合要求 |
| 400 | 邮箱不能为空 | email 缺失、为空或全为空格 |
| 400 | 邮箱格式不正确 | email 格式错误 |
| 400 | 邮箱长度不能超过 100 | email 长度超过 100 |
| 400 | 请求体格式不正确 | 请求体为空或 JSON 格式错误 |
| 409 | 用户名已存在 | name 与已有账号重复 |
| 409 | 邮箱已被占用 | email 与已有账号重复 |
| 500 | 服务器内部错误 | 其他异常 |

**补充说明**

- 密码在库中存储为 MD5 哈希值（32 位小写十六进制），接口任何情况下都不会返回密码。
- 用户名与邮箱的唯一性由数据库唯一约束保证，服务端在插入前先查重以给出具体提示。
- 服务端的非空、长度、格式校验使用 Bean Validation（字段上的 @NotBlank / @Size / @Email 注解），校验不通过时返回该字段注解中定义的提示语。前端也应做同样的校验，但那只是为了即时反馈，不能替代服务端校验。
- 用户名与邮箱入库前会去掉首尾空格，避免「张三」和「张三 」被当作两个不同用户名。

### 3. 查询当前用户信息

**GET /users/me**

返回当前登录用户的基本信息。用户 id 从 token 中解析，不接受前端传入。

**请求头**

| 请求头 | 值 |
|---|---|
| Authorization | Bearer {token} |

**请求参数**

无。

**成功响应**

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {
    "id": 1,
    "name": "张三",
    "email": "zhangsan@example.com"
  }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| id | long | 用户 id |
| name | string | 用户名 |
| email | string | 邮箱，可能为 null |

**失败情况**

| code | msg | 触发条件 |
|---|---|---|
| 401 | 未登录或登录已过期 | 未携带 token 或 token 无效 |
| 404 | 用户不存在 | token 有效但对应账号已不存在 |

**补充说明**

响应体中不包含 password 字段。服务端在密码字段上使用 Jackson 注解，保证该字段不参与 JSON 序列化。

### 4. 修改当前用户密码

**PATCH /users/me/password**

修改当前登录用户的密码，需提供原密码进行校验。

**请求头**

| 请求头 | 值 |
|---|---|
| Authorization | Bearer {token} |
| Content-Type | application/json |

**请求体**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| oldPassword | string | 是 | 原密码明文 |
| newPassword | string | 是 | 新密码明文，长度 6-20 |

**请求示例**

```json
{
  "oldPassword": "abc123456",
  "newPassword": "xyz987654"
}
```

**成功响应**

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": null
}
```

**失败情况**

| code | msg | 触发条件 |
|---|---|---|
| 400 | 新密码长度需为 6-20 位 | newPassword 不符合长度要求 |
| 400 | 新密码不能与原密码相同 | 新旧密码一致 |
| 400 | 原密码不正确 | oldPassword 与库中哈希比对失败 |
| 401 | 未登录或登录已过期 | 未携带 token 或 token 无效 |

**补充说明**

前端表单通常还有一个「确认密码」输入框，该字段用于避免用户输入笔误，属于前端校验范畴，在提交前即可拦截，因此本接口不接收。若确需服务端二次校验，可增加 rePwd 字段并校验其与 newPassword 相等。

### 5. 修改当前用户邮箱

**PUT /users/me/email**

修改当前登录用户的邮箱。

此处路径定位到 email 这一具体字段，属于对子资源的整体替换，因此使用 PUT 符合语义。

**请求头**

| 请求头 | 值 |
|---|---|
| Authorization | Bearer {token} |
| Content-Type | application/json |

**请求体**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| email | string | 是 | 新邮箱，需符合邮箱格式，长度不超过 100 |

**请求示例**

```json
{
  "email": "newmail@example.com"
}
```

**成功响应**

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": null
}
```

**失败情况**

| code | msg | 触发条件 |
|---|---|---|
| 400 | 邮箱格式不正确 | email 格式错误 |
| 401 | 未登录或登录已过期 | 未携带 token 或 token 无效 |

**补充说明**

当前 user 表的 email 字段没有唯一约束，允许不同账号使用相同邮箱。若业务上要求邮箱唯一（例如用于找回密码），需在表上增加唯一索引，接口相应增加 409 邮箱已被占用。

## 附录：待确认事项

1. 密码长度约定为 6-20 位明文。MD5 结果为固定 32 位十六进制，表中 password 列余量充足，明文长度限制可调整。
2. 密码采用无盐 MD5 存储。MD5 计算速度快（GPU 每秒可算数十亿次）且相同密码产生相同哈希，安全性低于 BCrypt，存在被暴力破解和彩虹表命中的风险。如需提升，最低成本方案是加盐后 MD5，更稳妥的做法是改用 BCrypt。
3. 修改密码成功后是否强制重新登录，涉及 token 失效策略，待定。
